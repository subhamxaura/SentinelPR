01 · Executive summary

Executive summary

SentinelPR is a production-grade, multi-tenant SaaS platform that watches three independent quality signals for software teams:

  • PR intelligence — deterministic static analysis plus optional AI review of every pull request, published to GitHub as check runs and inline comments;
  • Visual regression — Playwright-driven screenshot capture, pixel-diff scoring, DOM-structure signatures and explicit versioned baselines;
  • Synthetic monitoring — cron-scheduled multi-step browser journeys with latency percentiles and availability tracking.

All three signals fold into one explainable four-dimension risk score (Code · Security · Experience · Production) per pull request, surfaced through a dark-theme developer dashboard with command palette and keyboard navigation.

Verdict: the platform is feature-complete for a public launch. All 93 unit tests pass, the strict TypeScript build is clean, the production bundle compiles, both local and OAuth authentication modes are verified end-to-end, and the repository carries a complete delivery pipeline (CI gate → image build gate → GHCR release → dependabot). The remaining work items are external integrations (real GitHub App credentials) and product polish — not engineering gaps.

What makes the build distinctive

  • No simulated data. Every metric, finding, latency figure and risk score in the product is computed from real execution — the docs and UI refuse to fabricate state.
  • Determinism first. The review pipeline works with zero AI dependencies; the AI model is an optional enhancement with schema-validated, hallucination-defended output.
  • Security posture by construction. SSRF guard, HMAC-verified webhooks, signed expiring artifact URLs, hashed session tokens, secret-redacting logs, and RBAC enforced identically in UI and API.
  • Observability without dependency bloat. Prometheus/OTel-compatible worker metrics emitted from a hand-rolled registry — zero new packages.
02 · System architecture

System architecture

The platform is a single Next.js 16 application (dashboard + REST API) plus three independent BullMQ worker processes sharing PostgreSQL, Redis and an artifact store. Untrusted work (browser automation, repository analysis) never runs inside request handling.

GitHub ──webhook──▶ Next.js API (23 routes) ──enqueue──▶ Redis / BullMQ │ 15 dashboard pages │ ▼ ▼ PostgreSQL (25 models) ┌─ review-worker (rules + AI + GitHub) │ ├─ visual-worker (Playwright + pixelmatch) ▼ └─ synthetic-worker (11-step journeys) Artifact store (local FS / S3) │ /metrics (Prometheus·OTel)

Processing pipelines

① Pull-request review

Webhook → HMAC verification → idempotency ledger → diff fetch → 14 deterministic rules → optional AI review (zod-validated) → unified risk score → check run + inline comments.

② Visual regression

Suite enqueue → Chromium capture (animation freeze, standardised viewports) → pixelmatch diff + 32px-grid change-cluster localisation → DOM signature compare → candidate baseline → explicit approve.

③ Synthetic monitoring

BullMQ job scheduler (cron, pause/resume) → 11-action step executor → per-step results → P50/P95/P99 latency, availability, consecutive-failure streaks → auto-resolving alerts.

④ Unified risk engine

Folds finding weights, credential-leak severity caps, visual diff ratios and production health into one score with human-readable reasoning and a recommended action.

Security & multi-tenancy

Trust boundaries and controls

SurfaceControl
GitHub webhooksConstant-time X-Hub-Signature-256 HMAC validation; delivery-id idempotency ledger blocks replay and double-processing.
Browser automation targetsSSRF guard resolves DNS and blocks loopback, RFC1918, CGNAT, link-local/169.254.169.254 metadata and private IPv6 before any fetch; opt-in override for local dev only.
SessionsOpaque 256-bit cookie token; database stores only its SHA-256 hash; HttpOnly + SameSite=Lax (+ Secure in production); 7-day sliding expiry; sign-out deletes the row.
OAuth flowHMAC-signed, expiring state (CSRF defense); post-login redirects restricted to same-origin paths (open-redirect defense, unit-tested).
ArtifactsHMAC-SHA256 signed, expiring access tokens; no public bucket semantics.
AuthorizationRole matrix (owner > admin > member) as pure, unit-tested code; enforced in every mutating route; owners immutable; last-owner demotion/removal blocked; audit log records real actor identity.
SecretsStructured logger auto-redacts tokens/keys/credentials; rules engine flags 8 secret families in diffs; .env never committed.
OnboardingInvites and access requests are admin-approved; transactional, race-safe membership grants.
Residual risks (documented, not hidden): the metrics endpoint is unauthenticated and must stay on the internal network (hardening checklist item); local mode is explicitly localhost-only; AI review is optional and its output is schema-checked but still advisory.
06 · Operations & delivery

Operations & delivery

Deployment story

  • One image, four roles. The multi-stage Dockerfile (node:22-bookworm-slim + Chromium + system libs) runs the dashboard, any of the three workers, or migrations by changing only the container command.
  • Compose profiles. docker compose up -d starts infra only; --profile app brings the full stack with health-gated ordering and a shared artifacts volume.
  • Release channel. Pushing v* tags re-verifies the commit, publishes the image to GHCR with full semver tag fan-out, and creates a GitHub release. CI builds the same image on every push, so releases hit a warm cache.
  • Upkeep. Dependabot groups minor/patch and isolates majors across npm, GitHub Actions and the Docker base image.

Observability

# Per-worker scrape endpoint (default :9464/metrics) sentinelpr_queue_depth{queue="review",state="waiting"} 4 sentinelpr_queue_active_jobs{queue="review"} 2 sentinelpr_queue_jobs_total{outcome="completed",queue="review"} 127 sentinelpr_queue_job_duration_seconds_bucket{...,le="60"} 118 sentinelpr_worker_up{worker="review-worker"} 1

Series map onto OpenTelemetry semantic conventions, so an OTel Collector (Prometheus receiver) or Grafana Agent produces native OTLP data for dashboards. Depth is sampled from Redis live on each scrape; Redis or port failures degrade to labelled zeros and never affect job processing.
